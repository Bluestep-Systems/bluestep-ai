# Type-check diagnostics on a publish (read by `/b6p-push` step 5 when `typeCheckDiagnostics` is above `0`)

Since b6p 1.0 the **platform** builds every push (the CLI bundles no compiler), from each `tsconfig.json` in the draft, and reports its diagnostics. `typeCheckDiagnostics` is the platform's whole ERROR + WARNING count; `typeCheckErrors` lists up to 20 of them in the script's own sources (`file`, `line`, `column`, `code`, `message`, `severity`); a `.d.ts` never counts. They are **warnings** — the push exits `0` — unless `--fail-on-type-errors` was passed. A build the platform does not vouch for (`buildVouched: false`) is not published until it builds cleanly. The `diagnostics` in the `compile` block of a gateway `write_script_draft` come from the platform's own compile instead — the `bluestep-reference` skill's `reference/server-side-compile.md`. Treat them as real; do not wave them through. A correctly pulled component reports `0`, except in the two cases below, where the count never reaches `0` and a real error hides in the noise — so compare the diagnostics themselves, not just the count.

The first two cases below were seen with the CLI's own build (b6p 0.8); whether the platform's build reports them the same way has not been checked.

- **Every platform name is `Cannot find name` / `Cannot find namespace`** (`B`, `Java`, `Bluestep`, `console`, your query consts, the `MEFR_*` types) **on an older-layout component** (one with `draft/info/metadata.json` and `draft/objects/imports.ts`) — its `draft/tsconfig.json` does not list `"../declarations/**/*.d.ts"` in `include`, and the publish type-check wires `declarations/` in only through that list. Add that entry to `include` and publish again: in the reported case the count fell from 80 to 14, and 6 of the 14 were real errors the noise had hidden. Of the rest, a `/// <reference path="…/scriptlibrary" />` error is the dead directive `conventions/formula-patterns.md` already names. (As reported 2026-10 on b6p 0.8.1, not re-run here; the CLI fix is tracked as b6p-cli#38.)
- **`Cannot find module 'https://files.bluestep.net/…'`** (TS2792) on a component that imports a shared library by URL, such as `genericComponents.js` — the CLI's type-check of `scripts/` counted it, so that component never reached `0` (on 0.8.x it always exited 1). It is not an error in your code; leave the import as it is. Count it out and treat anything else as real. (As reported 2026-10, not re-run here; the CLI fix is tracked as b6p-cli#34.)

- **`Cannot find name` on a platform global or an imported query/field name** (`B`, your query-group consts, …) — the declaration is genuinely missing: the `declarations/` were not pulled, or the name was never imported into *this* component (rule 8: never fabricate references). Re-pull the component, or add the import on the platform and pull again. A `/// <reference … />` directive is not the fix — the build already wires the declarations in.
- **`Cannot find name` on one of your own symbols** — an ordinary type error in your source; fix it.
- **A stray unescaped backtick** inside a `B.out` template literal cascades into bogus `Cannot find name` diagnostics and produces a genuinely broken `app.js` — rule it out with the `bluestep-reference` skill's `conventions/ts-in-template-literal.md`.
- **Client-bundle diagnostics.** A MergeReport `static/` bundle can use browser-only third-party globals it declares nowhere (GridStack, Swal). With the CLI's own build (b6p 0.8 and 0.9) those were left out of the count; how the platform's build counts them is not yet checked. See the `bluestep-reference` skill's `gotchas/third-party-lib-type-noise.md`.
- **Re-pushing does not clear real diagnostics** — they are deterministic. Fix the cause, then publish again.
